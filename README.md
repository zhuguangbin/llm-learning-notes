# LLM 系统工程地图

本文梳理大语言模型从基本原理到工程实践的知识体系，涵盖模型结构、推理系统、训练系统与框架性能工程四个方向，并给出分阶段的学习路径与验收标准。

**在线阅读：<https://zhuguangbin.github.io/llm-learning-notes/>**

## 适用读者与视角

本大纲面向具备一定工程基础、希望系统了解大语言模型技术栈的读者，尤其适用于从事推理服务部署、训练平台建设或 GPU 集群运维的工程人员。阅读前应具备 Python 编程能力、Linux 使用经验，以及分布式系统的基本概念。

需要说明的是，本大纲采用**系统与平台工程的视角**，而非算法研究的视角。内容重心在于计算成本的构成、系统瓶颈的定位与工程实现的取舍，对模型效果调优、评测榜单与算法创新的覆盖较为有限。

### 三个基础估算公式

以下三式应能脱离参考资料直接使用，后续各章在讨论容量规划与性能瓶颈时会反复引用：

```
权重显存  = 参数量 × 每参数字节数
KV Cache = 2 × L × H_kv × d_head × S × B × sizeof(dtype)
训练算力 ≈ 6ND                    N 为参数量，D 为训练 token 数
```

## 两条可选的阅读顺序

二者覆盖内容一致，区别仅在于进入顺序，选择依据是产出周期而非难度。

**完整路径**适用于系统性学习，按 M0 至 M4 顺序推进，对应十二周计划。优点是概念铺垫充分，缺点是产出周期较长。

**推理优先路径**适用于当前工作与推理服务直接相关的读者。先完成 M0 与 M1 中与推理相关的最小子集（约需半天），随后直接进入第三章的入门路径，完成后再回补其余内容。该路径将可验证的实践环节前置，反馈更快，其内容对应十二周计划的第四至第八周。

## 第三章入门路径

本路径共八个阶段，须按顺序进行。每阶段设有验收标准，未达成前不宜进入下一阶段。合计约需十至十一天有效学习时间。

| 阶段 | 时长 | 内容 | 验收标准 |
|---|---|---|---|
| 0 | 约半天 | 前置知识准备 | 能说明 decode 阶段引入 KV Cache 的原因，并给出所用模型每 token 的 KV Cache 字节数 |
| 1 | 约一天 | 理解 prefill 与 decode 的阶段差异 | 能解释批大小为一时利用率显示接近百分之百、而实际算力利用率仅为个位数百分比的现象 |
| 2 | 约一天 | 建立性能测量基线 | 获得集群的基线延迟与吞吐关系曲线，并能指出曲线拐点位置及成因 |
| 3 | 约两天 | KV Cache 管理与 PagedAttention | 能独立绘制 block table 结构，说明分页机制缓解了哪一类显存碎片 |
| 4 | 约两天 | 请求调度与连续批处理 | 所实现引擎吞吐量明显高于 `generate()` 接口，且能指出提升来自代码的哪一部分 |
| 5 | 约一至两天 | vLLM V1 源码研读 | 绘制请求生命周期的调用链路图，标注各环节的数据结构 |
| 6 | 约两天 | 配置参数的对照实验 | 形成参数效果对照表，每项配置记录首 token 延迟、token 间延迟与吞吐量 |
| 7 | 按需安排 | 推理架构进阶 | 提出架构改进建议，并说明每项预期改善的具体指标 |

其中有两处排序需要说明。

**测量基线（阶段 2）安排在所有优化措施之前**，原因在于缺少基线数据时，后续任何优化都无法判断实际效果。将其前置后，每掌握一项技术均可当日在真实环境中验证。

**源码研读（阶段 5）安排在自行实现之后**，而非之前。先完成一次独立实现，再阅读工业级代码，能够清晰识别自身实现中简化的环节；顺序颠倒则容易停留在结构模仿的层面。

## 已有中文资料的覆盖情况

**主要缺口：第三章推理系统缺乏对应材料。** 已收集的资料中没有一份涉及推理引擎的实现原理，包括分页注意力、连续批处理、量化与投机解码，以及主流引擎的源码。对于从事推理服务运维的读者，这恰是与日常工作关联最紧密且具备实践条件的方向，应优先补充。

**次要缺口之一：框架性能工程的深入内容。** 中文 PyTorch 教程多以框架使用为主，未覆盖 torch.compile 内部机制、Triton 内核编写与 Nsight 性能归因。

**次要缺口之二：训练基础设施与强化学习系统。** 并行策略的覆盖较为充分，但分布式检查点、容错与弹性训练、推理引擎与训练引擎共存等问题尚无对应材料。

价值容易被低估的两份材料：**Ultra-Scale Playbook 中文版**（第四章并行策略最合适的单一材料）与 **How to Scale Your Model 的 GPU 章节**（以 Roofline 模型的语言将硬件特性、通信开销与并行策略整合为可计算的分析框架，恰好衔接第一章与第四章）。

完整的资料对应表与补充资源清单见[在线版](https://zhuguangbin.github.io/llm-learning-notes/)。

## 使用建议

**建议从代码进入，将论文作为解释代码的辅助材料。** 脱离实现直接阅读论文，短期内可积累术语，但难以形成稳定的理解。

**每完成一章，应用自己的语言写出该章的核心权衡。** 每个模块都围绕若干组明确的取舍展开——显存与通信的交换、延迟与吞吐的平衡、精度与性能的折中。无法清晰表述这些取舍，通常说明该章尚未真正掌握。

**实践环节应尽可能在真实环境中完成。** 推理与训练的多数问题只在一定规模下才会显现，玩具环境难以复现真实瓶颈。
