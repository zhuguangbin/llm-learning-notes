计算基础

单位约定

本章统一采用十进制表示存储容量，即 1 GB = 109 字节，与显卡标称容量的口径一致；涉及缓存分块时使用 KiB = 1024 字节。混用两种口径会带来约百分之七的偏差，在容量规划中足以导致误判，因此建议在实际工作中也明确声明所用口径。

1.1矩阵乘法的成本模型

Transformer 中绝大部分计算是矩阵乘法，因此成本模型只需要一个。设 A 的形状为 M×K，B 的形状为 K×N，二者相乘得到 M×N 的输出矩阵。输出中的每个元素是 K 项乘积之和，即 K 次乘法与 K 次加法，共 2K 次浮点运算。输出共有 M×N 个元素，因此：

FLOPs = 2 · M · N · K        ← 系数 2 来自乘法与加法各计一次
Bytes = (M·K + K·N + M·N) × 每元素字节数

其中 Bytes 是这次运算需要从显存读取和写回的数据总量：读入 A 与 B，写出 C。将二者相除，得到本章最重要的概念：

算术强度 (arithmetic intensity) = FLOPs / Bytes      单位：FLOP/Byte

其物理含义是：每从显存搬运一个字节的数据，能够换来多少次浮点运算。这个比值决定了一次计算究竟受限于硬件的算力还是显存带宽，是后续全部性能分析的共同坐标。

1.2算术强度与性能拐点

任何一款加速卡都有两个独立的上限：峰值算力与显存带宽。以 H200 SXM 为例：

指标H200 SXM
显存容量141 GB HBM3e
显存带宽4.8 TB/s
BF16 稠密算力≈ 495 TFLOPS
FP8 稠密算力≈ 990 TFLOPS

将峰值算力除以显存带宽，得到该硬件的性能拐点（ridge point）：

495 × 10¹² FLOPS ÷ 4.8 × 10¹² B/s ≈ 103 FLOP/Byte

这一数值的含义是：只有当计算任务的算术强度超过 103 时，才有可能将算力利用起来；低于该值时，无论硬件算力多强，性能都由显存带宽决定。这就是 Roofline 模型的核心，本章只需掌握这一个数字的用法。

两个真实场景的对比

场景 A：prefill 阶段的大矩阵乘法。设 M = N = K = 4096，采用 BF16：

FLOPs = 2 × 4096³              ≈ 1.37 × 10¹¹
Bytes = 3 × 4096² × 2          ≈ 1.01 × 10⁸
算术强度 ≈ 1365 FLOP/Byte      远高于 103 → 算力受限

场景 B：decode 阶段的矩阵向量乘法。每次仅生成一个 token，输入形状为 batch × hidden，而权重矩阵形状为 hidden × out。由于批规模远小于权重矩阵的维度，显存搬运量几乎全部来自权重：

FLOPs ≈ 2 · B · K · N
Bytes ≈ K · N × 2              仅权重，激活可忽略

算术强度 ≈ 2·B·K·N / (2·K·N) = B
本章最重要的推论

decode 阶段的算术强度约等于批大小。因此在 H200 上，当批大小低于 103 时，decode 必然处于带宽受限状态——计算单元大部分时间在等待显存，而非在进行运算。

由此可以直接推出一条基本原则：提升推理吞吐量的首要手段是增大批规模，而不是更换算力更强的硬件。第三章中的连续批处理、分页 KV Cache、投机解码等技术，全部是在这一约束下展开的。

这条推论同时解释了运维中的一个常见困惑：nvidia-smi 显示 GPU 利用率接近百分之百，但服务吞吐并不理想。该指标仅表示存在内核正在执行，并不区分计算单元是在运算还是在等待显存。判断真实状态需要依据算术强度，或参考 Nsight 报告中的显存吞吐指标。

1.3反向传播的三倍关系

训练一步包含前向与反向两个过程，其计算量存在固定的比例关系：

  • 前向传播：每个参数参与一次乘加运算，因此每个 token 约需 2N 次浮点运算，N 为参数量。
  • 反向传播：需要分别计算两个梯度——对输入的梯度（用于向前一层传递）与对权重的梯度（用于参数更新），每项各需 2N，合计 4N。

二者相加，每个 token 约需 6N 次浮点运算。乘以训练数据总量 D，得到训练算力的经验公式：

C ≈ 6 · N · D                  N 为参数量，D 为训练 token 数

推理侧只有前向过程，因此生成一个 token 约需 2N 次浮点运算。

用法示例

训练一个 7B 模型，使用 2T token：

总算力  = 6 × 7×10⁹ × 2×10¹²  = 8.4 × 10²² FLOPs
单卡有效算力 = 495 TFLOPS × 40% MFU = 1.98 × 10¹⁴ FLOPS
所需卡天 = 8.4×10²² ÷ 1.98×10¹⁴ ÷ 86400 ≈ 4910 卡天

1024 卡 → 约 4.8 天

其中 MFU（Model FLOPs Utilization，模型算力利用率）指实际达成的算力占峰值算力的比例。BF16 预训练达到百分之四十至五十属于正常水平，该指标将在第四章详细讨论。

1.4交叉熵与困惑度

语言模型的训练目标为交叉熵损失，困惑度与其的关系为：

ppl = exp(loss)

需要建立两个数值锚点，用于快速判断训练状态：

其一，随机猜测对应的损失值等于词表大小的自然对数。Llama 3 的词表规模为 128256，因此 ln(128256) ≈ 11.76。若模型损失长期停留在该数值附近，说明尚未学到任何有效信息，通常意味着学习率、初始化或数据管线存在问题。

其二，损失下降 0.1 所对应的实际改善幅度。以 exp(2.0) = 7.39 与 exp(1.9) = 6.69 为例，困惑度降低了百分之九点五。这解释了为何在预训练后期，损失值 0.01 的改善也值得投入资源争取。

1.5数值格式

本节只需掌握一条原则：指数位决定动态范围，尾数位决定精度。

格式符号 / 指数 / 尾数字节关键特征
FP321 / 8 / 234基准格式
TF321 / 8 / 104张量核心的内部格式，存储仍占 4 字节
BF161 / 8 / 72指数位与 FP32 相同，动态范围一致
FP161 / 5 / 102精度较高但范围较窄，最大值 65504
FP8 E4M31 / 4 / 31用于前向的权重与激活
FP8 E5M21 / 5 / 21用于梯度，需要更大的动态范围
INT8 / INT4整数 + 缩放因子1 / 0.5量化格式，需要校准
为何业界从 FP16 转向 BF16

FP16 仅有 5 位指数，最小正规数约为 6×10⁻⁵。训练后期的梯度经常小于该量级，会直接下溢为零并导致训练发散。规避手段是损失缩放（loss scaling），即将损失乘以一个较大系数再在更新前缩回，但该机制需要调参且存在失效风险。

BF16 的指数位宽度与 FP32 相同，动态范围一致，梯度不会下溢，因而无需损失缩放，直接消除了一整类训练故障。代价是尾数仅有 7 位、精度较低，但实践表明训练过程对动态范围的敏感度远高于对精度的敏感度。

1.6三个估算公式

本章的全部产出是以下三个公式，应当能够脱离参考资料直接使用：

① 权重显存 = 参数量 × 每参数字节数

② KV Cache = 2 × L × H_kv × d_head × S × B × sizeof(dtype)

③ 训练算力 ≈ 6 · N · D

公式 ② 中各项的含义：系数 2 对应需要缓存的 K 与 V 两份张量；L 为层数；H_kv 为 KV 头数，GQA 所压缩的正是这一项；d_head 为每个注意力头的维度；S 为序列长度；B 为并发请求数。这些参数均可直接从模型的 config.json 中读取。

1.7完整示例：Llama-3-70B 部署于 H200

从 config.json 中读取关键参数：层数 80，隐藏维度 8192，注意力头数 64，KV 头数 8，头维度 128，参数量 70.55B。

第一步：判断权重是否放得下

BF16: 70.55×10⁹ × 2 = 141.1 GB   > 141 GB，单卡放不下
FP8:  70.55×10⁹ × 1 =  70.6 GB   可以放下

这是一个具有代表性的结果：70B 模型在 BF16 精度下恰好超出单卡容量，必须采用张量并行（TP=2）或改用 FP8 量化。此类判断在选型阶段的价值很高，且只需一次乘法。

第二步：计算每 token 的 KV Cache 占用

2 × 80 × 8 × 128 × 2 字节 = 327,680 B = 320 KiB / token

第三步：估算可支持的并发规模

采用 FP8 权重、BF16 KV Cache，单卡部署：

可用于 KV 的空间 ≈ 141 − 70.6 − 10 = 60.4 GB
                              扣除的 10 GB 为激活值、框架开销与 CUDA 上下文

可容纳 token 总数 = 60.4×10⁹ ÷ 327,680 ≈ 184,000 tokens

  8K 上下文  →  184,000 ÷ 8192  ≈ 22 路并发
  2K 上下文  →  184,000 ÷ 2048  ≈ 90 路并发
 32K 上下文  →  184,000 ÷ 32768 ≈  5 路并发

第四步：回到算术强度

8K 上下文场景下仅有约 22 路并发，对应的算术强度约为 22，远低于 H200 的性能拐点 103。这意味着该部署在 decode 阶段处于明显的带宽受限状态，算力利用率不足四分之一。

若要提升利用率，唯一途径是增大批规模，而批规模又受限于 KV Cache 所能占用的显存。

本章与第三章的衔接

KV Cache 是推理吞吐的核心约束。这一结论解释了第三章中大半技术的存在动机：分页管理消除碎片以提高显存利用率、前缀缓存复用已有计算、KV 量化直接减半占用，其共同目标都是在有限显存内容纳更多并发请求，从而将算术强度推向性能拐点。

作为验证：将 KV Cache 改为 FP8 后，每 token 占用降至 160 KiB，8K 上下文下的并发从 22 路提升至 45 路，算术强度随之翻倍。这正是 KV 量化被视为独立于权重量化的一档收益的原因。

1.8可复用的估算工具

将上述流程固化为一个函数，便于在选型讨论中直接调用：

def plan(params_b, layers, kv_heads, head_dim,
         gpu_gb=141, w_bytes=1, kv_bytes=2, overhead_gb=10):
    """params_b: 参数量（十亿）; w_bytes: 权重每参数字节; kv_bytes: KV 每元素字节"""
    w  = params_b * 1e9 * w_bytes / 1e9
    kv = 2 * layers * kv_heads * head_dim * kv_bytes   # 每 token 字节数
    free = gpu_gb - w - overhead_gb
    toks = free * 1e9 / kv
    print(f"权重 {w:.1f} GB | KV {kv/1024:.0f} KiB/token | 可容纳 {toks:,.0f} tokens")
    for s in (2048, 8192, 32768):
        print(f"  {s//1024:>2}K 上下文 → {toks/s:.0f} 路并发")

plan(70.55, 80, 8, 128)                # Llama-3-70B, FP8 权重
plan(70.55, 80, 8, 128, kv_bytes=1)    # 同上，KV 改为 FP8

需要说明的是，该函数给出的是理论上限。实际可用并发还会受到调度器预留、显存碎片、CUDA Graph 捕获所需空间等因素影响，通常比估算值低百分之十至二十。其用途在于快速判断量级与方案可行性，精确数值仍需以实测为准——这正是第三章阶段 2 要求先建立性能基线的原因。

1.9本章练习

本章的验收标准是：能否迅速估算出单卡可支持的并发规模。以下三题用于检验，建议先独立完成再查看解答。

练习 1 · 并发估算

Qwen3-32B 的配置为：层数 64，KV 头数 8，头维度 128，参数量 32.8B。采用 BF16 权重与 BF16 KV Cache，部署于单张 H200，上下文长度 32K。可支持多少路并发？

查看解答 
权重     = 32.8×10⁹ × 2 = 65.6 GB
KV/token = 2 × 64 × 8 × 128 × 2 = 262,144 B = 256 KiB
可用空间 = 141 − 65.6 − 10 = 65.4 GB
token 数 = 65.4×10⁹ ÷ 262,144 ≈ 249,000
并发     = 249,000 ÷ 32768 ≈ 7 路

本题的要点在于：32B 模型看似不大，但在 32K 长上下文下并发仅有个位数。长上下文场景的成本主要由 KV Cache 而非权重决定，这一点在容量规划中经常被低估。

练习 2 · GQA 的价值

沿用 1.7 节的 70B 模型与配置，若它采用 MHA（KV 头数为 64）而非 GQA（KV 头数为 8），8K 上下文下的并发会变成多少？

查看解答 
KV/token = 2 × 80 × 64 × 128 × 2 = 2,621,440 B = 2560 KiB = 2.5 MiB
token 数 = 60.4×10⁹ ÷ 2,621,440 ≈ 23,000
并发     = 23,000 ÷ 8192 ≈ 2 路   （GQA 方案为 22 路）

KV 头数从 64 压缩到 8，并发能力提升为原来的八倍。GQA 并非精度上的妥协，而是一项将推理成本降低近一个数量级的结构改动——这解释了为何它已成为当前开源模型的标准配置。第二章将说明它在效果上的代价为何可以接受。

练习 3 · 训练周期估算

训练一个 32B 模型，使用 10T token，可用资源为 256 张 H200，MFU 按百分之四十五计算。需要多长时间？

查看解答 
总算力   = 6 × 32×10⁹ × 10×10¹² = 1.92 × 10²⁴ FLOPs
单卡有效 = 495×10¹² × 45% = 2.23 × 10¹⁴ FLOPS
集群算力 = 256 × 2.23×10¹⁴ = 5.70 × 10¹⁶ FLOPS
耗时     = 1.92×10²⁴ ÷ 5.70×10¹⁶ ≈ 3.37×10⁷ 秒 ≈ 390 天

本题的意义在于结论本身：256 张卡不足以支撑这一训练任务。折算为约 10 万卡天，若要在两个月内完成，需要约 1600 张卡。这类估算应当在立项阶段完成，而非在训练启动数周后才发现资源不足。

此外需注意，上述计算尚未计入故障恢复、检查点写入与数据加载等开销。实际项目通常还需在此基础上追加百分之十至二十的时间余量。

1.10小结

本章的内容可以压缩为四条：

  1. 算术强度是全部性能分析的共同坐标，等于计算量除以显存访问量。
  2. 硬件的性能拐点等于峰值算力除以显存带宽，H200 在 BF16 下约为 103 FLOP/Byte。低于该值即为带宽受限。
  3. decode 阶段的算术强度约等于批大小，因此推理吞吐的首要杠杆是增大批规模，而批规模受制于 KV Cache 显存。
  4. 三个估算公式：权重显存、KV Cache、训练算力 6ND。

其中第三条是本章与第三章之间的桥梁。理解了「批规模受 KV Cache 约束，而算术强度又约等于批规模」这一链条，第三章中分页管理、前缀缓存、KV 量化、连续批处理等技术的动机便都不需要额外解释了。

下一章进入模型结构原理，说明 Transformer 各组件分别消耗多少算力与显存。本章建立的成本模型将在其中反复使用。
